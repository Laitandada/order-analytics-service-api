## Architectural Analysis of the Bottleneck

The optimized implementation significantly improved throughput and latency by reducing the order lookup from multiple sequential Prisma round-trips to a single SQL statement with JSON aggregation.

However, the production-build benchmark still exceeded the p95 < 50 ms target under 200 concurrent VUs.

The optimized benchmark achieved:
- 1,019.28 requests/second
- 0.21% error rate
- 112.80 ms p50
- 205.21 ms p90
- 260.60 ms p95
- 672.62 ms p99

Additional investigation showed that database-call latency increases under concurrent load, while the configured connection pool introduces contention when 200 concurrent VUs compete for a smaller number of database connections.

A controlled EXPLAIN ANALYZE experiment also showed that supplying the partition key (`orderedAt`) enables PostgreSQL partition pruning and reduces planning time from 6.242 ms to 3.659 ms.

The p95 < 50 ms target was therefore not achieved in the final benchmark. Further optimization could include connection-pool tuning, read scaling, caching, and additional query/partition optimization, but these were not introduced solely to manipulate the assessment benchmark.
